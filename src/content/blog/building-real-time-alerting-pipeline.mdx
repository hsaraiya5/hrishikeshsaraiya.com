When you're building software for continuous glucose monitors, latency isn't just a performance concern — it's a safety requirement. A patient who is hypoglycemic needs an alert in seconds, not minutes. When I joined the alerting team at Dexcom, our pipeline had a median latency of ~45 seconds end-to-end. We needed to get that down, significantly.

This is the story of how we redesigned the alerting pipeline from the ground up using Apache Kafka and Go, and cut that latency to under 18 seconds at the 99th percentile.

## The Original Architecture

The legacy system was a classic polling-based architecture: a cron job running every 30 seconds would query the main PostgreSQL database for new glucose readings, evaluate alert conditions, and enqueue notifications. Simple to understand, easy to operate — but fundamentally latency-constrained by the polling interval.

```
CGM Device → Ingestion API → PostgreSQL
                                ↓ (poll every 30s)
                          Alert Evaluator
                                ↓
                          Notification Queue
```

The problems were obvious in retrospect:

- The 30-second poll added up to 30 seconds of inherent latency before we even touched alert logic
- The evaluator was stateless, so every poll re-fetched 24 hours of history to detect trends
- A single evaluator process was a bottleneck; we couldn't parallelize per-patient

## Redesigning with Kafka

The core insight was that every glucose reading is an **event**, and we should treat it like one. Instead of polling for new readings, we wanted to stream them as they arrived.

We set up a Kafka topic `glucose.readings` with partitioning by device ID. This gave us:

1. **Guaranteed ordering** — readings for a device are always processed in the order they were generated
2. **Natural parallelism** — we can run N consumer instances, each owning a subset of partitions
3. **Replay capability** — if the evaluator crashes, it resumes from its last committed offset

```go
// Consumer group setup
reader := kafka.NewReader(kafka.ReaderConfig{
    Brokers:   cfg.Brokers,
    Topic:     "glucose.readings",
    GroupID:   "alert-evaluator",
    MinBytes:  10e3, // 10KB
    MaxBytes:  10e6, // 10MB
    MaxWait:   500 * time.Millisecond,
})
```

## Stateful Alert Evaluation

The trickiest part was trend detection. Algorithms like "rate of change alert" need recent history — you can't evaluate them statelessly. Our solution: a per-device in-memory sliding window, backed by Redis for durability.

```go
type GlucoseWindow struct {
    DeviceID  string
    Readings  []Reading // last 30 minutes
    mu        sync.RWMutex
}

func (w *GlucoseWindow) Push(r Reading) {
    w.mu.Lock()
    defer w.mu.Unlock()
    cutoff := r.Timestamp.Add(-30 * time.Minute)
    w.Readings = append(filterBefore(w.Readings, cutoff), r)
}
```

Each consumer instance owns a set of partitions and maintains windows only for those devices. On startup, it hydrates from Redis before beginning to process.

## Results

After a 4-week phased rollout:

| Metric | Before | After |
|--------|--------|-------|
| P50 latency | 38s | 8s |
| P99 latency | 74s | 18s |
| Evaluator CPU | 85% | 22% |
| False positive rate | unchanged | unchanged |

The CPU drop was a pleasant surprise — eliminating the repeated history queries reduced database load significantly, and the Go consumers were far more efficient than the Python evaluator they replaced.

## What I'd Do Differently

- **Schema registry from day one.** We started with JSON and migrated to Avro halfway through, which was painful. Always set up a schema registry before you have producers in production.
- **Dead letter queues.** We added these later; they should have been in the initial design. Malformed readings were silently dropped in v1.
- **Chaos testing.** We didn't simulate consumer crashes until a week before go-live. Test your recovery path early.

Real-time systems are genuinely hard to get right, especially in regulated environments where you can't just ship fast and iterate. But the combination of Kafka's durability and Go's concurrency model made this one of the more satisfying architectural challenges I've worked on.
